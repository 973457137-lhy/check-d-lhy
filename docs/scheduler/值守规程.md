### 元信息交付纪律（2026-11-04 M3 定，已踩两次打回）

交付「行数 / 字节 / 哈希」时，四条缺一不可：

1. **哈希必须绑时点**：写「`<时点> 盘上件：N 行 / M B / sha256 abcd…`」。
   同一行数 ≠ 同一版本；字节不同就是不同版本，不要当成漂移去解释。
2. **行数必须绑末字节**：写清末尾有没有 LF。`wc -l` 数的是 LF 个数，末尾无换行会少算一行。
3. **版本表不用「修订前 / 修订后」**：改成「版本号 + mtime + 行/字节/哈希」并列，
   否则会被读成同一版在两个时点漂移。
4. **字节级核验只能发附件，不能贴正文**：HTML 转义与换行归一会改字节，对方无法复算。
   流程：`agent_mail_upload_attachment` 拿 `file_id` → `SendMessage` 的 `file_refs` 引用 →
   正文里写明 `expires_at`（过期需重传）。
5. **每封交付邮件正文末尾固定带两行**（M3 2026-11-04 定，比改文件更省——文件不动、哈希不漂、审计可追）：

   ```
   发信地址：973457137@qq.com
   发信时点：<YYYY-MM-DDTHH:MM:SSZ>
   ```

   **记录时必须分两栏**（M3 2026-11-05 定）：`作者自报时点` 与 `服务端 created_at` 并列，
   不合并、不取平均、不互相校正。实测两者差几秒（如自报 04:51:28Z / 服务端 04:51:36Z，差 8 秒），
   两者都对；混写就会重演「同一封两个时点」的争议。

   文件何时因实质内容修订，再把「发信地址 + 时点」并进版本表。
6. **凡涉及数字或状态变化的件，三人（M0/M1/M3）同抄**。只抄一部分人，是今天三次数字漂移
   （6→7→9、7/15/20→9/15/24/20、251↔252）的共同根因。
