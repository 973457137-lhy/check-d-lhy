> 版本 V1.0 · 2026-10-28 · 团队协作版（不含个人身份信息）  
> **内部完成目标：2026-11-08 前形成可演示、可访问、可复现的作品**  
> **计划方法：参照 obra/superpowers `writing-plans` 的「明确接口—可测试任务—验收关卡」方式组织。**

## 0. 一页决策摘要

**作品定位：** CheckD——面向大学生学习、课程与科研任务的智能规划 Agent；建议申报「教育智能体专项赛道 / AI+教学科研」。

**作品闭环：** 腾讯 WorkBuddy 接收自然语言 → 通过受控工具读取 CheckD 任务与日历 → 拆解任务 → 调度器生成可行方案 → 预览变更 → 用户确认 → 写回 CheckD → 再读取核验并记录执行结果。

**四人四模块：** 队长（CheckD 核心 API/集成）、同学 A（腾讯 WorkBuddy Agent）、同学 B（调度引擎）、同学 C（用户体验/评测与演示）。各自拥有独立目录与 PR，必要共享接口由队长在 10/29 冻结。

**只做 MVP：** ①读任务与日历 ②自然语言拆解任务 ③生成无冲突计划 ④临时事件后重排 ⑤经批准写入并验证。历史计时反馈作为加分项，若 11/04 前仍不稳定则延后。

**不能忽略：** 比赛要求在 **腾讯官方 WorkBuddy** 上完成智能体开发、提供有效可访问链接，不能只做 CheckD 内置聊天框；所有团队贡献及第三方开源组件必须披露；评测可随机测试，不能靠静态截图替代真实执行。

**现实限制：** 目前未能通过连接的 GitHub 账户读取 CheckD 仓库，因此本计划的代码目录/API 均是**建议接口，不是已核实的真实文件路径**。队长须让本地 Codex 扫描仓库后修订文件级任务，不得未经核对直接改库。

## 2. 架构边界与最低实现

```text
腾讯 WorkBuddy（指定比赛入口 / 可访问 Agent）
       │    意图理解、知识库、工作流、工具调用
       ▼
CheckD Tool Adapter（校验身份、参数、权限、返回状态）
       │                               └─ 安全审计 / 工具日志
       ├──── CheckD 任务与日历业务服务（Supabase 等现有实现）
       │
       └──── Scheduling Engine（优先研究 Horolog；失败时降级为确定性规则排程）
                            │
                            └─ ScheduleProposal 预览 → 审批 → 提交 → 核验
```

**必须遵守 CheckD 原有产品语义：** Task 是事项；ScheduleBlock 是计划占用时间；TimerSession 是实际计时。Task 可以有多个 ScheduleBlock；不同任务的 Active TimerSession 允许重叠，任务时长各自累计，全局主动专注时长对重叠区间只计一次。调度不能把 TimerSession 当作未来可用时间，也不能偷偷改写既有计时逻辑。

**最小演示闭环：** 事先准备不少于 3 组经脱敏的课程、任务和突发会议样本；用户问“明天需要做什么”、再问“把项目报告拆解并安排”，最后插入临时会议，Agent 生成重排方案，用户确认后写入，再读取校验最终时间块。任何步骤失败应有可见原因与安全退出路径。

## 3. 四人角色、代码所有权与验收

### 3.1 队长｜模块 M0：CheckD 核心接口、安全与集成（最终合并人）

**主责：** 现有 Task/Calendar/Supabase/TimerSession 代码审计；创建统一 API、Mock/真实数据开关、审批与日志边界；在自己的主仓库合并 PR；端到端集成与发布门禁。

**建议代码所有权（待 Codex 核对真实路径）：** `server/checkd-api/`、`server/agent-adapter/`、`docs/contracts/`、`.github/`；不要擅自让三位同学同时改核心数据库文件。

**可交付物：** `docs/contracts/agent-api-v1.md`、测试样例、可运行的只读任务查询、审批后写入接口、CI/PR 规则、集成记录、版本标签。

**完成定义 DoD：** ①A、B、C 可基于同一契约开发而不依赖本地真实密钥；②跨用户访问被阻止；③同一审批重复提交不造成重复任务；④批准前无正式写入；⑤已有计时/日历回归测试通过。

### 3.2 同学 A｜模块 M1：腾讯 WorkBuddy Agent 与工具编排

**主责：** 在腾讯官方 WorkBuddy 上创建真正可用的专家/Agent；配置人设、工作流、工具/MCP、知识库；输入校验、错误回复；测试分享链接、他人账号权限。

**建议代码所有权：** `integrations/workbuddy/`、`docs/workbuddy/`、`knowledge/agent/`（与 C 的评测资料目录分开）。平台侧配置需要导出或截图为可复现说明。

**可交付物：** 可访问 Agent 链接、三个核心场景的真实工具调用记录、WorkBuddy 配置说明、失败处理说明、联调视频/截图。

**完成定义 DoD：** ①不是纯提示词回答，有真实工具回调；②访问链接在队长以外的账号/环境有效；③不共享开发者个人凭据；④工具失败时不会宣称“已经保存”；⑤至少 3 个场景可复现。

**关键前置：** 10/29 前验证 WorkBuddy 能否从评委环境访问所选 MCP/API；若本地 MCP 不可达，立即改用平台支持的远程 HTTPS 工具或经允许的工作流托管方式。不可等到 11/06 才发现链接无效。

### 3.3 同学 B｜模块 M2：智能调度与动态重排

**主责：** 研究 Horolog 的排程约束与测试；对比许可后选定复用/适配方式；独立实现 `generate_schedule` 与 `repair_schedule` 的统一调用接口；提供确定性降级版本。

**建议代码所有权：** `services/scheduler/`、`tests/scheduler/`、`docs/scheduler/`。不得直接修改 WorkBuddy 平台配置和 CheckD 主数据模型。

**算法最低规则：** 固定课程/会议不可移动；任务时间块不得与硬约束冲突；尊重截止日期及可用时窗；不足以完成时返回未安排量；重排时尽量减少不必要的变更；相同输入应尽量得到稳定输出。

**可交付物：** `ScheduleProposal` 的输入输出契约示例、正常与异常样例、调度服务或模块、自动化测试、算法来源与开源声明。

**完成定义 DoD：** ①5 组构造用例无硬冲突；②插入临时会议后只调整必要的柔性任务；③无可行解能明确报出原因；④离线规则降级方案始终可运行。

### 3.4 同学 C｜模块 M3：交互体验、知识依据与评测证据

**主责：** 提供用户可理解的日程提案/前后差异展示；设计真实教育场景数据与知识库出处；编写测试脚本、演示步骤、性能记录；整理作品说明和匿名材料。

**建议代码所有权：** `tests/e2e/`、`fixtures/education/`、`docs/demo/`、`docs/submission/`；如确有可修改的前端，再在独立 UI 文件分支交付，避免与队长共享页面冲突。

**可交付物：** ≥3 条真实场景及预期结果、≥10 条边界/异常测试、可复现演示脚本、≤3 页初赛作品大纲、截图清单、OSS/匿名检查清单。

**完成定义 DoD：** ①操作前后变化可看懂；②截图与视频均来自真实运行；③有实际调用日志可核查；④材料没有密钥、真实身份和未脱敏个人数据；⑤非开发者按文档也能重复执行演示。

**设备限制处理：** 如果同学 C 没有合适的 macOS/Swift 编译环境，就不强行分配原生 Swift UI 开发；优先负责 WorkBuddy 内的交互设计、测试自动化、真实数据样本与提交材料，必要 UI 开发由队长掌控。

## 4. 跨模块接口契约：10/29 必须先冻结

以下为**建议 API 草案**，真实路径、参数、认证方式以 CheckD 代码审计后为准。接口文件应由队长单独管理，其他成员先用 Mock 构造响应。

| 能力 | 建议工具名 | 读/写 | 所属模块 | 返回/规则 |
|---|---|---|---|---|
| 查询任务 | `list_tasks` | 读 | M0 → M1 | 仅返回授权用户数据，包含任务 ID、优先级、截止时间、剩余时长 |
| 查询日程 | `get_calendar_events` | 读 | M0 → M1/M2 | 固定事件与柔性时间块可区分，明确时区 |
| 拆解任务 | `propose_task_breakdown` | 仅提案 | M1 | 子任务列表、预计时间、依据及不确定性 |
| 生成计划 | `generate_schedule` | 仅提案 | M2 → M1 | 新增/移动时间块及未排入原因，默认不写库 |
| 重排计划 | `repair_schedule` | 仅提案 | M2 → M1 | 变更差异、冲突原因、原计划版本 |
| 校验提案 | `validate_schedule` | 读/校验 | M0/M2 | 硬约束、权限、版本有效性 |
| 提交变更 | `apply_approved_changes` | 写 | M0 | 用户确认、服务端审批令牌、幂等键、成功后再查证 |

**统一状态：** `DRAFT → VALIDATED → PENDING_APPROVAL → APPLIED / REJECTED / EXPIRED / FAILED`。建议每个提案有 `proposal_id`、`base_version`、`changes[]`、`explanations[]`、`unplanned_tasks[]`；精确字段以真实代码和平台工具能力为准。

**最少测试约定：** 使用固定的假数据，不把个人课表直接发给外部开源项目；统一采用带时区的 ISO 8601 时间，明确北京时间；所有读工具不应有副作用；所有写工具由后端鉴权，不依赖 LLM 自称已获得同意。

## 6. PR 协作协议（四人必须一致）

**GitHub 流程：** 同学在自己账号 Fork 队长主仓库 → 本地 `origin` 指向本人 Fork、`upstream` 指向队长主仓库 → 从最新 `upstream/main` 创建 `feat/...` 分支 → 自己保存/提交/推送 → 向队长仓库 `main` 发起 Pull Request → 队长审核/测试/合并 → 其他人同步 `upstream/main` 后再开下一分支。**Fork 是远端仓库副本，不是 PR；代码不会自动出现在队长主仓库。**

```bash
# 每名队员第一次确认：
git remote -v
# 如果还没有 upstream，使用队长主仓库的真实地址添加：
git remote add upstream <队长主仓库URL>
# 开始一项新任务：
git fetch upstream
git switch main
git merge --ff-only upstream/main
git switch -c feat/<模块>-<功能>
# 开发测试完成后由队员本人操作：
git add <本次修改文件>
git commit -m "feat(<模块>): <简短功能>"
git push -u origin feat/<模块>-<功能>
# 然后在 GitHub 发起 PR：base=队长主仓库/main，compare=个人Fork/feat/...
```

**主仓库规则：** 仅队长合并；禁止直接 push `main`；首选 Squash merge；PR 至少有「目的、修改文件、测试命令与结果、风险、截图/日志、所依赖契约版本」；跨模块修改必须先沟通；有冲突由开发者在自己的分支解决，不让队长在主分支临时手动拼接代码。

**建议 PR 节奏：** 10/29 前接口 PR；10/30–11/01 每人 1–2 个小 PR；11/02–11/05 每天 1 次可测试 PR 或明确 blocker；11/06 起仅允许 hotfix。禁止单次 PR 混合几十个不相关文件。**Codex 可以写代码、运行测试、生成 PR 描述，但 git add/commit/push 由各自的人亲手操作。**

**命名建议：** `feat/checkd-api-read` / `feat/workbuddy-tools` / `feat/scheduler-basic` / `test/contest-e2e` / `docs/contest-submission`；Issue 标签 `M0` `M1` `M2` `M3` `P0` `P1` `blocked` `ready-for-review`。

**队长合并前检查：** ①与最近 main 无冲突 ②测试通过 ③没有密钥 ④只改自己模块或共享修改已批准 ⑤权限与审批正确 ⑥如引用开源代码已说明源仓库与许可证 ⑦影响现有计时/日历的改动已通过回归。

## 8. 评测计划与提交内容

### 必演示场景（真实执行，不是静态脚本）
1. **学习计划：** “帮我查看明天的任务与课程，把英语复习安排到空闲时间。”——应读取实际任务/事件并展示计划提案。
2. **复杂任务拆解：** “周五前完成科研报告，请拆成可执行子任务并分配时间。”——应生成结构化任务，用户确认后写入并回读。
3. **突发事件重排：** “下午新增一个固定会议，尽量少改其他安排。”——应维持固定事件、给出调整理由、确认后同步日历。

### 必测边界（至少 10 条）
- 空任务列表；没有可用空闲时间；已过截止日期；时间跨日；时区差异；固定事件冲突；任务预计时长大于可用总时长；重复批准同一个提案；审批后原日历被其他设备修改；登录失效/跨用户访问；工具超时/网络错误；LLM 错误提议移动固定课程；含不可信指令的知识库内容。

### 内部建议验收标准（不是比赛官方评分阈值）
- 三条核心场景各连续跑通 3 次；至少 10 条边界用例有可追溯结果；固定事项 0 次非法移动；用户未确认 0 次正式写入；禁止把未实际执行的结果显示为“执行成功”；Agent 链接外部账号真实可打开并执行核心工具。

### 材料分工与检查
- **C 主笔：** 作品≤3 页大纲、≥3 个提示词/结果截图、匿名材料、连续演示视频与可复现步骤。
- **A 提供：** WorkBuddy 链接、专家与工作流配置、知识库来源、工具调用结果。
- **B 提供：** 排程流程图、对照结果、算法局限、外部开源模块说明。
- **队长审定：** 作品原创/第三方披露、GitHub 稳定版、敏感数据与密钥、时间节点与最终打包。

## 9. 每日沟通与看板制度

- **每天午间 10 分钟站会（异步可替代）：** 昨天完成什么、今天交付什么、当前阻碍什么。
- **每天 21:30 统一展示：** 每位同学用 1–3 分钟展示真实可运行内容/测试结果，不能只报“完成 80%”。
- **每天 22:00 前：** 更新 GitHub Issue 和 PR；队长明确「已合并 / 需修改 / 阻塞」。
- **阻塞超过 2 小时：** 直接在群里发报错、运行命令、日志摘录与已尝试步骤（去敏），不要等晚会。
- **任务状态：** `Todo → In Progress → PR Ready → Review → Done`，额外标注 `Blocked`；每个任务都有唯一 Owner、截止日期、可验证的 DoD。
- **统一决策：** 修改共享 API 或演示范围由队长最终确认；重要决定写入 `docs/decisions/`，防止口头约定失效。
